## 원인

표지 보기와 목록 보기는 필터링된 전체 목록을 한 번의 커밋에 전부 장착했다. 카드 한 장이 MUI 서브트리와 `IntersectionObserver`를 들고 있어서, 600장이면 첫 커밋 하나가 수 초짜리 긴 작업이 된다.

더 큰 문제는 그다음이다. `PdfCoverItem`에는 메모가 없었고 `PdfListItem`의 `React.memo`는 기본 얕은 비교였는데, 페이지가 모든 핸들러를 인라인 화살표 함수로 넘기므로 비교가 매번 불일치한다. 그래서 부모가 다시 그릴 때마다 장착된 카드 전부가 다시 그려졌다.

## 수정

- `useProgressiveItems`(새 파일): 목록을 24개 묶음으로 위에서부터 장착한다. 묶음 사이에 32ms 디바운스를 두고 `requestIdleCallback`(없으면 즉시, 타임아웃 300ms)으로 다음 묶음을 붙인다. 마지막 항목 뒤 센티넬이 뷰포트 600px 안에 들어오면 한 번에 72개씩 건너뛴다. 폴더·검색어·보기 방식이 바뀌면 첫 묶음으로 되돌린다.
- `ListMountProgress`(새 파일): 센티넬과 "목록 불러오는 중 n/N" 표시. `data-list-mounted` · `data-list-rendered` · `data-list-total` 이 테스트 후크다.
- `thumbnailLoadQueue`(새 파일): 표지 이미지 동시 로드를 6개로 제한하고, 요청한 순서대로 슬롯을 준다. 20초 안에 끝나지 않는 이미지는 슬롯을 놓는다(이미지 로드 자체는 계속된다).
- `cardPropsEqual`(새 파일) + `PdfCoverItem` · `PdfListItem`의 `React.memo(..., cardPropsEqual)`: 데이터 프로퍼티가 같고 핸들러의 유무가 같으면 다시 그리지 않는다. 핸들러는 동일성이 아니라 존재 여부로 비교한다.
- 적용 화면: `FolderPage`, `SearchPage`, `TagPage` 의 목록 보기와 표지 보기. 선택·일괄 작업은 여전히 필터링된 전체 목록을 대상으로 한다(장착만 나눴다).

## 결과

같은 측정 스크립트, 같은 스텁, 같은 600건으로 잰 수치다. 숫자는 증거 파일에서 그대로 옮겼다.

| 측정 | 수정 전 (`before-fix-frames.json`) | 수정 후 (`after-fix-frames.json`) |
|---|---|---|
| 최장 프레임 멈춤 | **3858ms** | **389ms** (앱 부팅 + 첫 24장) |
| 다음 긴 멈춤들 | 3112 / 2813 / 1957ms | 123 / 119 / 117ms |
| 600장 모두 DOM 에 있는 시각 | 3889ms (한 커밋) | 6442ms (묶음 장착) |
| 스크롤 전 썸네일 요청 | 15 | 15 |
| 썸네일 동시 요청 최댓값 | 6 | 6 |

수정 전에는 600장이 한 커밋에 들어가면서 3.8초짜리 멈춤 하나가 났고, 그 뒤로도 3.1 · 2.8 · 1.9초짜리 멈춤이 이어졌다(카드 전체가 반복해서 다시 그려진 것). 화면이 멈춘 시간은 합쳐서 11초가 넘는다. 수정 후에는 첫 화면이 24장으로 먼저 뜨고, 이후 묶음마다 0.1초대로 끊기며 6.4초에 걸쳐 끝까지 채워진다. 전체 장착은 더 늦지만 그동안 화면은 계속 돈다 — 요구한 "넌블록킹"이 이것이다.

동시 요청 최댓값 6은 수정 전후가 같다. **이 수치만으로는 큐의 효과를 주장할 수 없다**: 같은 출처 HTTP/1.1 에서는 브라우저 자체가 호스트당 6개로 묶기 때문이다. 큐가 보장하는 것은 그 6개가 목록 위쪽 카드부터 순서대로 쓰인다는 점이고, 그 순서는 테스트의 `book-0001`~`book-0006` 단언으로 확인했다. HTTP/2 로 서비스될 때는 브라우저 상한이 없어지므로 큐가 유일한 제한이 된다.

`cover-thumbnail-browser.mjs` 는 이 테스트가 쓰는 Free 번들이 `serverThumbnails: true` 라서 `PdfCoverItem` 이 `ServerCoverThumbnail` 로 간다. 테스트는 브라우저가 PDF 를 직접 그려 만드는 옛 폴백("표지를 준비하는 중", 캔버스, 생성 썸네일 업로드)을 기대한다. 수정 전 코드에서는 더 앞 단계(`img` 6개 대기)에서, 수정 후에는 그다음 단계에서 멈춘다. 증거 파일의 카드 상태 덤프를 보면 1~6번은 `ready`, 404 를 주는 7번은 재시도 버튼과 함께 `failed`, 503 뒤 200 을 주는 8번은 `ready` 로 의도대로 동작한다. 이 테스트를 현재 동작에 맞게 고치는 일은 이번 변경 범위 밖으로 남긴다.

## 하지 못한 것

- **배포 컨테이너 검증.** 작업 중 라이브러리 CIFS 호스트 `//192.168.0.13/usbshare1` 가 Docker 에서 끊겼다(`docker run -v pdfit-usbshare1` → `host is down`, 새 마운트 시도 → `mount error(115) could not connect`). 호스트는 ping 에 응답하지만 445 세션이 서지 않는다. 그래서 `npm run deploy:standalone` 이 라이브러리 확인 단계에서 멈췄고, 떠 있는 컨테이너(이 작업의 중간 빌드)는 `GET /api/folders` 가 500 이다. 이 보고서의 수치는 모두 최종 번들(`apps/pdfit/dist`) 대상이며, 배포 컨테이너 대상 재검증은 호스트 복구 뒤로 남긴다.
- **Pro 대상 브라우저 테스트.** 서버(15201)가 떠 있지 않아 실행하지 못했다.
- **기존 실패 3건의 원인 규명.** `cover-thumbnail-browser` 는 이 번들이 `serverThumbnails: true` 라 옛 브라우저 폴백을 기대하는 테스트가 맞지 않는 것으로 확인했고, `ai-auto-tag-browser` · `dialog-copy-layout-browser` 는 이 변경 전에도 실패한다는 사실만 확인했다. 셋 다 고치는 일은 이번 범위 밖이다.

## 덧붙임 — Playwright 1.54.2 → 1.65.0

번들 브라우저를 설치할 수 없었다. Playwright 1.54.2 의 설치 코드가 Node 26 에서 제거된 `fs.promises.rmdir(..., { recursive: true })` 를 부른다(`ERR_INVALID_ARG_VALUE ... 'options.recursive' is no longer supported`, 내려받기는 100% 완료 후 정리 단계에서 실패). 이 PC 에는 Node v26.4.0 하나뿐이라 구버전으로 우회할 수 없어, 사용자 지시로 `playwright` 를 1.65.0 으로 올렸다. 설치가 통과해 build 1254(Chrome for Testing 158)를 받았고, 위 회귀는 모두 그 브라우저로 돌렸다.
