# Tablet opened time, viewer routing, and loading

## Environment

- 2026-10-01 13:12 KST, Windows 11, local root Docker Compose `service` at
  `http://127.0.0.1:15201` (healthy).
- Playwright Chromium and WebKit, tablet emulation at 810 CSS pixels and touch;
  desktop control at 1280 CSS pixels.
- Existing folder/tag PDFs; loading target `코어 코틀린.pdf` (16 MB).

## Steps, logs, and outcome

1. `npm run build --workspace @pdfit/pdfit` and
   `npm run build --workspace service`: pass.
2. `docker compose up -d --build --wait --wait-timeout 60 service`: pass;
   `docker compose ps service`: healthy.
3. `node apps/pdfit/tests/tablet-opened-at-browser.mjs`: pass on tablet folder,
   tablet tag, desktop folder, desktop tag. Tablet text was
   `2026. 09. 30.\n오후 04:50`; desktop retained one line. After scrolling, the
   tablet menu opened the drawer; the cover link used `/viewer/`.
4. The same test with `--webkit`: pass on all four profiles/routes.
5. `node apps/pdfit/tests/tablet-viewer-loading-browser.mjs --tablet-only`:
   pass. HEAD 7 ms, full GET 13,863 ms, first canvas 16,582 ms. Toolbar stayed
   at y=47.75; annotation rail stayed at x=12 before and after continuous
   scroll.
6. The same test with `--webkit`: pass. HEAD 20 ms, full GET 27,365 ms,
   first canvas 45,852 ms. Toolbar stayed at y=47; annotation rail stayed at
   x=12 before and after continuous scroll.
7. `git diff --check`: pass.

## Failures and reproducibility

- First Chromium loading test had a test-only timeout waiting for a second
  legacy page shell; first page and viewer controls had loaded. The test was
  corrected to check the actual continuous scroll area and rerun successfully.
- A prior 4 MiB range threshold took about 65 seconds for this 16 MB file;
  a custom range transport took about 29 seconds and timed out beyond 90
  seconds for an 84 MB document. Both experiments were reverted. The retained
  20 MiB full-download behavior remains sensitive to Google Drive response
  time, especially in WebKit. No PDF-byte throughput improvement is claimed.
- The user photograph shows Safari at `/api/folders/by-id/...`, a native PDF
  view rather than `/viewer/...`; that route has no PDFit sidebar or toolbar.
  Cover links now use `/viewer/` even with Safari long-press/new-tab navigation.
- A physical iPad and the public `pdfit.io` deployment were not tested here;
  these results are repeatable against the local Compose service only.
