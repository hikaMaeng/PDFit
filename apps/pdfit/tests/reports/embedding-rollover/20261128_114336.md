# 임베딩 스케줄 중첩 검증 보고서

2026-11-28 11:43:36 KST. [검증 계획](../../plans/embedding-rollover-20261128.md)

## 실행 결과

`npm run build:pdfit`이 성공했다. 격리 PostgreSQL 17.10과 pgvector 0.8.6에서 임베딩, 스케줄러, OCR, 콘텐츠 검색 테스트 28건을 실행했고 모두 통과했다.

- 빈 조회를 막은 동안 계획을 두 차례 호출했다. 조회를 풀자 한 번만 더 확인했다.
- 대기 중인 2,000건의 원문을 모두 수정해 기존 예약을 무효화했다. 큐 크기 2,000건을 유지하면서 최신 본문을 예약할 수 있었다. 그 사이 삽입한 문서의 변경 기록은 용량을 확보한 뒤 작업으로 등록됐다.
- 앞의 100건을 다시 수정하는 동안 변경 위치 뒤에 있던 50건이 먼저 등록됐다. 커서를 한 바퀴 돈 뒤 앞의 수정 100건도 다시 처리 대상으로 잡혔다.
- 200ms 간격 스케줄에서 첫 HTTP 응답을 보류하고 계획 세 차례, 원문 수정 두 차례, 새 문서 삽입 한 차례를 겹쳤다. 동시에 진행한 HTTP 요청은 최대 한 건이었다. 요청은 구버전 한 건, 최종 수정 한 건, 신규 문서 한 건이었다. 저장 테이블과 검색 결과에는 최종 수정과 신규 문서만 있었다.
- `429` 뒤 스케줄러와 서비스 인스턴스를 교체했다. 다음 세 차례 계획에서는 추가 호출이 없었다. 테스트 DB에서 재개 가능 시각을 넘기자 대기 작업 두 건이 완료됐다.

격리 Free Docker의 `http://127.0.0.1:15922/health`는 200이었다. Docker 상태는 `healthy`, 재시작 횟수는 0이었다. 1분 간격으로 돌린 기존 Chromium 시나리오는 68,890 UTF-16 단위 OCR의 끝 문구 수정까지 검색했다. 요청 최대 동시 실행은 1건, 처음과 수정 이후의 최대 배열 폭은 각각 3과 2였다. **의미 검색** 탭과 `semantic-search-results`를 사용했다. 캡처 네 장과 요청 기록은 `test/20261128/embedding-rollover-browser/`에 있다.

## 재현 범위

테스트 DB를 `PDFIT_TEST_DATABASE_URL`에 지정하고 `node --test packages/pdfit/tests/embedding-rollover.test.mjs packages/pdfit/tests/background-tasks.test.mjs packages/pdfit/tests/ocr.test.mjs packages/pdfit/tests/content-search.test.mjs`로 실행한다. 브라우저 회귀는 `apps/pdfit/tests/embedding-search-browser.mjs`의 합성 공급자 모드로 실행했다. 겹침 시나리오는 짧은 주기로 재현했다. 운영 서재의 한 시간 단위 처리량과 장기 적체는 이번에 측정하지 않았다.
