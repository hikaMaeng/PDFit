# Display-name translation timeout report

- Timestamp: 2026-11-12 15:46 KST
- Environment: Windows 11 Pro, Docker Desktop, built-in Chromium pane
- URLs: `http://127.0.0.1:15203` (Free standalone), `http://127.0.0.1:18180` (apibond AI server on the Docker host)
- Change under test: `apps/pdfit/src/server/services/displayTranslation.ts` — `AbortSignal.timeout(20_000)` -> `AbortSignal.timeout(300_000)`

## Steps and results

1. Host AI server inventory: `GET http://127.0.0.1:18180/v1/models` returned one model id, `qwen36-35b` (`owned_by: apibond`): passed.
2. Container reachability for port 18180, run inside `pdfit-pdfit-1`: `127.0.0.1` -> `000` (no connection), `host.docker.internal` -> `200`, `192.168.0.6` -> `200`, `172.17.0.1` -> `000`. The stored url therefore uses `host.docker.internal`: passed.
3. Upstream path check on the host: `POST /v1/chat/completions` -> `200`, `POST /chat/completions` -> `404`. The stored url keeps the `/v1` suffix because the service appends `/chat/completions`: passed.
4. Registered the AI server: `POST /api/settings/ai-servers` -> `201 {"id":707}`; `GET /api/settings/ai-servers` returned `url: http://host.docker.internal:18180/v1`, `models: {"llm":"qwen36-35b"}`: passed.
5. Model latency measured from inside the container, before the change: `POST /v1/chat/completions` with a one-word prompt answered `200` in `12.45 s`, and its payload carried a long `reasoning_content`: observed.
6. Before the change, `POST /api/settings/translations` with `["Science Fiction","History"]` answered `{"error":"TimeoutError: The operation was aborted due to timeout"}`; a second single-label attempt failed the same way: reproduced (this is the defect the change addresses).
7. `npm run deploy:standalone` rebuilt the image (`sha256:67ccacb85a61cb47712663d0e3418ac10ec4946add3b79f82abd47e768ecd8bd`), removed and recreated `pdfit-pdfit-1`, and the container reported `healthy`; startup log: `[pdfit] Library index ready: 719 PDFs across 2 folders.`: passed.
8. The AI server row survived the container recreation: `GET /api/settings/ai-servers` returned id `707` unchanged: passed.
9. After the change, `POST /api/settings/translations` with `["Science Fiction","History"]` answered `http=200` in `total=34.50 s` with `{"translations":["과학 소설","역사"]}`. 34.50 s exceeds the removed 20 s limit, so the old build could not have produced this reply: passed.
10. Headless pane at `/settings` rendered the stored row: `local-qwen36 | OpenAI compatible | http://host.docker.internal:18180/v1 | LLM: qwen36-35b`: passed.

## Disproved hypothesis

The first failure looked like an unreachable AI server. Step 2 and step 5 cleared that: the container reaches the server and gets a `200`, only slowly. The cause was the client-side 20 s abort, not connectivity, DNS, or the url path.

## Not covered

- Only the `llm` role is configured; `vision` and `embedding` are empty, and no vision or embedding path was exercised.
- The 300 s ceiling itself was not driven to the limit; the longest observed upstream reply was 34.50 s.
- Pro (`apps/service`) was not built, deployed, or tested.
