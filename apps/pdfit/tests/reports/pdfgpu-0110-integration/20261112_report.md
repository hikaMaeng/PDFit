## 찾은 회귀와 대조 실험

0.1.10에 변경 전(HEAD) 뷰어 컴포넌트를 붙여 배포하고, 키보드만 쓰는 스크립트로 확인했다(`20261112_key-spread-control/negative-control-head-components.json`).

| 증상 | 변경 전 코드 + 0.1.10 | 수정 후 |
|---|---|---|
| PDF.js 양쪽 보기 PageDown | (1,2) → (2,3) → (4,5) → (6,7). 2쪽이 겹침 | (1,2) → (3,4) → (5,6) |
| GPU, 뷰포트 포커스에서 PageDown 1회 | 1 → 3 (두 페이지) | 1 → 2 |

GPU 가로 스와이프는 처음 실행할 때 `1 → 2 → 1`로 되돌아갔다. 호출 스택을 기록해 보니, `loadPhase === 'ready'`에서 저장된 페이지를 적용하는 PDFit effect가 스와이프 약 600ms 뒤 `scrollToPage(0)`을 불렀다. 단언 `the turned page must not snap back`을 추가해 확인했다.

- 방지 코드를 뺀 빌드: `actual '1'`, `expected '2'`로 실패 (`20261112_snapback-control/without-guard.txt`)
- 넣은 빌드: 통과 (`with-guard.txt`)

옛 고정 버전(0.1.9-pdfit.1, HEAD 코드)을 별도 worktree에 빌드해 같은 정적 서버로 비교했다. 그 빌드에서는 GPU 스와이프 두 종류가 모두 통과했다.

## 버린 가설

- **"`ee2a32e`의 페이지 모드 스크롤 추종이 되돌아감의 원인"** — 아니다. 처음에 pdfgpu 작업 트리(최신)의 `controller.ts`를 읽고 이렇게 의심했다. 그런데 `ee2a32e`는 `v0.1.10` 이후 커밋이라 고정본에 없다. 고정본 `dist/viewer/controller.js`는 페이지 모드에서 `interaction.page`를 그대로 쓴다. 원인은 PDFit의 초기 페이지 effect였다.
- **"GPU 터치 스와이프 실패도 결함"** — 아니다. 기대값 `3`은 0.1.9 정규화(홀수 페이지가 앞)에 묶여 있었다. 그 규칙은 표지를 단독으로 둔 GPU 레이아웃의 (2,3) 행에서 오른쪽 페이지에 착지하던 동작이고, pdfgpu `6745d6f`(F11)가 고친 것이다. GPU 기대값을 `2`로 바꿨다.
- **"0.1.10의 2D 대체 경로 중단으로 WebGPU 없는 환경이 깨진다"** — 확인하지 못했다. `ef2ac86`은 WebGPU 캔버스에서 오류가 난 뒤의 2D 전환만 막은 것이다. 이번 검증은 WebGPU가 되는 Chrome에서만 돌렸다.
