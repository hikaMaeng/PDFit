## 확인 결과

- PDF 두 페이지를 업로드했다. 페이지 OCR API로 텍스트 레이어를 읽은 뒤 수정 API로 68,890 UTF-16 코드 단위의 본문을 저장했다. 0부터 센 68,808번째 위치의 `tailuniquetext`가 두 시나리오에서 원래 PDF의 1페이지 결과로 나왔다. 64,000 단위까지 저장하는 기존 키워드 색인에서는 그 단어가 검색되지 않았다.
- 공급자 앞의 HTTP 기록에서 모든 배치가 `input` 배열로 전송됐다. 두 시나리오에서 각각 검색 요청 다섯 건을 함께 보냈다. 합성 공급자는 응답 배열을 뒤집었고 `data[].index`를 기준으로 붙인 결과가 검색됐다. 배열 3개짜리 첫 배치 응답을 일부러 보류한 동안 유일한 공용 워커에서 다른 페이지의 OCR이 완료됐다.
- 합성 벡터 환경에서 기존 본문 끝부분만 수정했다. 이전 결과는 조회에서 사라졌다. 다음 주기는 배치 폭 2로 수정한 `newuniquetailedit`을 색인했고 같은 페이지에서 검색됐다. 두 런타임은 종료 전 `ready`를 보고했다. 브라우저와 테스트 공급자가 기록한 오류는 0건이었다.
- 페이지 OCR·클립 OCR·클립 메모·일반 코멘트의 결과를 실제 API에서 확인했다. 브라우저의 **의미 검색** 탭과 `semantic-search-results`를 따라 원본 링크를 읽고, **코멘트 열기**에서 대상 UUID의 코멘트를 열었다. AI Settings 후보 선택은 접근 가능한 입력 이름과 선택 항목의 정확한 이름으로 확인했다.
- 모델별 테이블에는 `id`, `contents`, `ref`, `refid`, `embedding`, `hnsw` 여섯 열이 있었다. `pg_indexes`에서 두 테이블 모두 `hnsw` 열의 `vector_cosine_ops` HNSW 인덱스를 확인했다.
- 기존 OCR 캐시 복구를 따로 실행했다. 잘린 64,000자 레거시 투영을 재현한 뒤 캐시에서 PostgreSQL 문자 단위 68,892자와 수정한 끝 문구를 복원했다. 전체 책 목록 함수는 호출되지 않았다.
- 격리 DB에서 트랜잭션 안에 변경 표식 100,000개를 넣고 `EXPLAIN (ANALYZE, BUFFERS)`를 실행했다. `embedding_dirty` 인덱스로 100행을 읽고 잠그는 쿼리의 실행 시간은 0.103ms였다. 쿼리를 마친 뒤 트랜잭션을 롤백했다.

## 재현과 증거

`npm run build:pdfit` 후 컨테이너 두 개에서 격리 포트에 연결했다. 테스트는 [`embedding-search-browser.mjs`](../../embedding-search-browser.mjs)로 실행했다. 합성 공급자는 테스트가 직접 만들며 실제 공급자 주소는 `PDFIT_TEST_LIVE_EMBEDDINGS`로 넘겼다. 회귀 테스트는 작업 스케줄러·OCR·기존 검색·자동 태그 관련 파일 6개에서 57건 통과, 1건 보류였다. 보류한 항목은 별도 DB URL을 요구하는 기존 키워드 검색 테스트다. 새 통합 시나리오는 실제 격리 PostgreSQL을 사용했다.

- 합성 벡터 기록과 Chromium 캡처 `test/20261128/embedding-search-final-fixture/`
- 실제 모델 기록과 Chromium 캡처 `test/20261128/embedding-search-final-real-model/`
- 각 폴더의 `results.json`에 본문 길이, 끝 문구 위치, 요청 폭·동시성, 검색 결과를 남겼다. `01`부터 `04`까지 후보 설정, 선택 결과, 끝 문구 검색, 코멘트 연결을 담았다.
