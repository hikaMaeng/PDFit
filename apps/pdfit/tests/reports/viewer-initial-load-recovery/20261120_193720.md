# Initial PDF load recovery test report

## Observation and environment

2026-11-20 19:37 KST. Free production logs at 19:29–19:30 KST recorded a 10.488-second library refresh returning 503, followed by immediate 503 responses for the reported PDF. A subsequent read from the same LAN address returned HTTP 206 and valid PDF bytes. Chromium rendered the reported book on the existing production build. The logs establish the sequence, while the detailed reason for the initial disk delay was unavailable.

The candidate was built with `npm run deploy:standalone` in an isolated Free Compose project on loopback port 15235. Docker reported `healthy` and `/health` returned 200.

## Executed checks

- `node --test packages/pdfit/tests/library-volume-guard.test.mjs` passed 5/5. Folder counts skipped PDF-by-PDF stats. Six delayed stats with combined latency above the guard deadline still returned a complete listing. A genuinely hung or unavailable volume still triggered isolation.
- `node apps/pdfit/tests/viewer-initial-load-recovery-browser.mjs` passed 3/3. Two initial HEAD 503s recovered automatically. Six consecutive 503s exhausted the retry budget, and **다시 시도** then reopened the PDF. A 404 displayed the missing-document message after a single request. Chromium reported zero page errors.
- Both new retry messages are present in all eight primary locales.
