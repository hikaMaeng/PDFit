# Free 임베딩 검색 검증 계획

작성일 2026-11-27

## 목표와 환경

Free의 OCR 저장, 시간별 작업, pgvector 검색, 브라우저 의미 검색을 이어서 확인한다. 격리 컨테이너는 `/app/data`를 tmpfs에 두며 `127.0.0.1:15922`에만 공개한다. `PDFIT_TASK_INTERVAL_MINUTES=1`로 시간별 실행을 앞당긴다. 공용 워커는 한 슬롯이다. Chromium은 Windows 호스트에서 실행한다.

## 절차와 통과 조건

1. `/health`가 200인지 확인한다. PDF를 업로드해 실제 페이지 OCR 경로로 텍스트 레이어를 읽은 뒤 페이지 텍스트 수정 API로 장문을 저장한다. 고유 끝 문구의 위치는 64,000 UTF-16 코드 단위 이후다. 기존 키워드 조회와 의미 검색에서 각각 확인한다.
2. 브라우저에서 기본 LLM과 임베딩 후보를 저장하고 선택한다. 합성 벡터의 기본·인덱스 차원은 4/2다. 배치 크기 3을 사용한 뒤 2로 바꾼다. 테스트 HTTP 서버에는 모든 입력이 배열로 도착하고 각 주기에서 설정한 배치 크기에 도달해야 한다. 동시 검색 호출 중에도 최대 진행 중 요청 수는 1이다. 테스트 공급자는 벡터 응답의 순서를 뒤집어 `index` 처리도 확인한다. 첫 3개 배치 응답을 보류한 상태에서 다른 페이지 OCR이 완료되어야 한다.
3. 의미 검색에서 고유 끝 문구와 원래 PDF의 1페이지 링크를 확인한다. 클립 OCR·클립 메모·일반 코멘트도 찾아 원본 ID를 확인한다. 일반 코멘트는 링크로 선택한 코멘트가 열려야 한다.
4. 끝 문구만 고쳐 다시 저장한다. 직전 색인에서 옛 문구가 사라지고 다음 주기가 수정한 끝 문구를 다시 찾으면 통과한다. 로컬 모델 연동에서는 실제 768차원 벡터로 같은 최초 색인과 검색을 재현한다.

## 실행과 증거

`npm run build:pdfit` 후 격리 Free 런타임의 포트를 환경 변수 `PDFIT_TEST_BASE_URL`로 넘긴다. `PDFIT_TEST_CHROMIUM_PATH`에는 설치된 Chrome을 지정한다. `PDFIT_TEST_OUTPUT`에 실행 기록과 캡처를 남긴다. 실제 모델은 `PDFIT_TEST_LIVE_EMBEDDINGS`에 로컬 `/v1/embeddings` 주소를 지정한 별도 실행에서 사용한다. 실행 진입점은 `node apps/pdfit/tests/embedding-search-browser.mjs`다.

설정에서는 **서버 추가**, **기본 임베딩 모델**과 차원 입력의 이름을 사용한다. 결과는 이름이 **의미 검색**인 탭의 `semantic-search-results` 안에서 확인한다. HTTP 로그에는 요청별 배열 폭, 진행 중 요청 수, 끝 문구 포함 여부만 기록한다.
